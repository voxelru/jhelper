# jhelper

Flask-приложение для планирования задач из Jira: выборка по JQL, диаграмма «сотрудник × дата» с прямоугольниками трудозатрат.

Приложение **читает** задачи из Jira по JQL и умеет **точечно записывать** два изменения — исполнителя задачи и плановые трудозатраты (ширину прямоугольника), — когда пользователь явно нажимает «Сохранить в Jira». Никаких других полей приложение в Jira не меняет.

## Возможности

- Подключение к Jira (Server / Data Center) по **логину и паролю** (HTTP Basic Auth)
- Выбор задач по **JQL** из файла настроек
- Диаграмма:
  - **сверху** — даты (выходные на шкале не занимают место)
  - **слева** — сотрудники
  - **прямоугольники** — задачи в 3 строки: ключ со статусом, название, заказчик
  - ширина прямоугольника = плановые трудозатраты в рабочих днях
  - приглушенный цвет по **приоритету**
  - значок `!` рядом с ключом, если в Jira не заполнены дата начала, дата окончания или трудозатраты
  - задачи с **назначенным в Jira сроком** (дата начала или окончания из `fields.start_date`/`fields.end_date` с `source: jira_field`) встают на диаграмме фиксированно на эту дату; остальные задачи заполняют свободные промежутки **подряд без зазоров**, в порядке приоритета — как раньше
- Выпадающий **фильтр по спринту** в шапке страницы (значение берётся из поля Jira, настроенного в `fields.sprint`)
- Ссылки с ключей задач ведут в Jira, если задан `JIRA_BASE_URL`
- Всплывающая подсказка по задаче показывает ключ, название, заказчика, даты начала/завершения и трудозатраты
- **Перетаскивание задач между сотрудниками** меняет исполнителя:
  - смена сразу видна в UI (задача помечается как несохранённая) и копится в локальный файл `pending_changes.json`;
  - перетаскивание **внутри строки одного сотрудника** — это только смена порядка, в Jira не уходит;
- **Изменение ширины прямоугольника** (перетаскивание правого края) меняет плановые трудозатраты задачи в UI и тоже копится в `pending_changes.json` до сохранения
  - в Jira ничего не отправляется, пока не нажата кнопка **«Сохранить в Jira»** — она сохраняет и смены исполнителя, и изменения трудозатрат одним действием;
  - до сохранения изменения переживают перезагрузку страницы (хранятся в файле на сервере), но не переживают повторный запрос `/api/board` от другого клиента, если тот сохранит поверх — данные читаются из этого же файла, поэтому конфликтов «последний выигрывает» стоит избегать при многопользовательской работе
- Горизонт планирования настраивается (по умолчанию 90 календарных дней)
- Задачи без исполнителя **не показываются**

## Требования

- Python 3.10+
- Доступ к Jira REST API (`/rest/api/2/search`/`/issue` или `/rest/api/3/search`/`/issue`)
- Учётная запись с правом **чтения** задач по вашему JQL **и правом смены исполнителя** (assignee) на задачах, которые может редактировать пользователь — это нужно для кнопки «Сохранить в Jira». Если такого права нет, кнопкой пользоваться нельзя, но чтение и просмотр доски продолжат работать.

## Настройка

### 1. Учётные данные Jira

Скопируйте `.env.example` в `.env` и заполните:

```env
JIRA_BASE_URL=https://jira.example.com
JIRA_USERNAME=login
JIRA_PASSWORD=secret
```

| Переменная       | Описание                          |
|------------------|-----------------------------------|
| `JIRA_BASE_URL`  | Базовый URL Jira без `/` в конце  |
| `JIRA_USERNAME`  | Логин                             |
| `JIRA_PASSWORD`  | Пароль                            |

Файл `.env` в git не коммитится.

### 2. Бизнес-настройки — `config/app_settings.yaml`

#### JQL

```yaml
jql: 'assignee is not EMPTY AND statusCategory != Done ORDER BY priority DESC'
```

Рекомендуется оставлять условие `assignee is not EMPTY`: задачи без исполнителя всё равно отфильтровываются на стороне приложения.

#### Приоритеты и цвета

Имена должны совпадать с `priority.name` в вашей Jira:

```yaml
priorities:
  order:
    - Highest
    - High
    - Medium
    - Low
    - Lowest
  colors:
    Highest: "#b85c5c"
    High: "#c68452"
    Medium: "#c2a24f"
    Low: "#6f9a76"
    Lowest: "#73879a"
    default: "#7f8f9b"
```

- `order` — порядок в очереди сотрудника (первый = самый высокий приоритет)
- `colors` — заливка прямоугольников; неизвестный приоритет берёт `default`

#### Горизонт планирования

```yaml
planning_horizon:
  kind: calendar_days   # или working_days
  count: 90
```

| `kind`           | Смысл |
|------------------|--------|
| `calendar_days`  | `count` календарных дней от сегодня; на шкале только рабочие дни внутри интервала |
| `working_days`   | `count` рабочих дней подряд; выходные не занимают место на шкале |

#### Трудозатраты (ширина блока)

```yaml
effort:
  type: timetracking_original
  jira_field_id: null

min_effort_working_days: 1
working_hours_per_day: 8
```

| `effort.type`             | Источник |
|---------------------------|----------|
| `timetracking_original`   | `timetracking.originalEstimateSeconds` → дни через `working_hours_per_day` |
| `timetracking_remaining`  | `timetracking.remainingEstimateSeconds` |
| `number_field`            | Число из поля (`jira_field_id`, напр. `customfield_10016`) как рабочие дни |
| `seconds_field`           | Число из поля как секунды → дни через `working_hours_per_day` |

Если оценка отсутствует или нулевая, используется `min_effort_working_days` (по умолчанию **1 md**).

#### Масштаб шкалы

```yaml
pixels_per_working_day: 36
```

#### Дополнительные поля Jira

```yaml
fields:
  customer:
    jira_field_id: null  # например customfield_10100

  sprint:
    jira_field_id: null  # например customfield_10007

  start_date:
    source: board        # board или jira_field
    jira_field_id: null  # например duedate / customfield_...

  end_date:
    source: board
    jira_field_id: null
```

- `fields.customer.jira_field_id` — кастомное поле Jira для заказчика; значение выводится 3-й строкой в блоке задачи и в подсказке.
- `fields.sprint.jira_field_id` — поле Jira со спринтом (обычно `customfield_XXXXX` от Jira Software); значение используется для выпадающего фильтра по спринту в шапке страницы. Поддерживаются оба формата поля Sprint — и современный (список объектов), и устаревший строковый формат Jira Server/DC.
- `fields.start_date` и `fields.end_date` — источники дат в подсказке **и** позиции задачи на диаграмме.
- `source: board` — задача заполняет свободные дни в очереди сотрудника (старая логика, без привязки к датам).
- `source: jira_field` — если поле в Jira заполнено, задача встаёт на диаграмме фиксированно на эту дату (по дате начала, а если она не задана — вычисляется от даты окончания и трудозатрат); если поле не заполнено или не распознано, задача возвращается к старой логике и заполняет свободные дни.

## API

| Метод | Путь            | Описание |
|-------|-----------------|----------|
| `GET`  | `/`             | Страница диаграммы |
| `GET`  | `/api/settings` | Настройки для UI (горизонт, цвета, рабочие даты, источники полей, минимальные трудозатраты, URL Jira) |
| `GET`  | `/api/board`    | Данные доски: строки сотрудников, задачи, список спринтов для фильтра и метаданные для подсказок |
| `GET`  | `/api/pending`  | Список несохранённых изменений (из `pending_changes.json`) |
| `POST` | `/api/pending`  | Добавить/обновить несохранённую смену исполнителя. Тело: `{"key", "assigneeId", "assigneeName", "originalAssigneeId"}`. Если `assigneeId` совпадает с `originalAssigneeId`, запись удаляется (откат к исходному) |
| `POST` | `/api/pending/effort` | Добавить/обновить несохранённые плановые трудозатраты (ширину прямоугольника). Тело: `{"key", "effortDays", "originalEffortDays"}`. Если `effortDays` совпадает с `originalEffortDays`, запись удаляется (откат к исходному) |
| `POST` | `/api/save`     | Отправить все несохранённые изменения в Jira (смену исполнителя и/или трудозатраты, `PUT /rest/api/{2,3}/issue/{key}`). Успешные части удаляются из pending-файла, неудачные остаются и возвращаются в `failed` (с полем `field`: `assignee` или `effort`) |

Приложение пишет в Jira только по явному действию пользователя (кнопка «Сохранить в Jira») и только два поля: исполнителя (`assignee`) и плановые трудозатраты (`timetracking` или настроенное кастомное поле — см. `effort.type`). Остальные поля (названия, даты, приоритеты, статусы и т.п.) приложение в Jira не меняет.

Перетаскивание задачи **внутри строки одного сотрудника** меняет только порядок на экране (в Jira не пишется, не сохраняется между перезагрузками страницы).

## Как устроена диаграмма

1. Задачи загружаются по JQL и группируются по исполнителю.
2. При загрузке запрашиваются стандартные поля Jira (`summary`, `assignee`, `priority`, `status`, `timetracking`) и дополнительные поля из `effort`/`fields` (см. `collect_jira_fields` в `board_logic.py`), включая спринт.
3. Внутри строки задачи сортируются по `priorities.order`.
4. Задачи с назначенным в Jira сроком (`fields.start_date`/`fields.end_date` с `source: jira_field` и заполненным полем) встают фиксированно на эту дату. Остальные задачи раскладываются в свободных промежутках слева направо без зазоров: ширина блока ∝ трудозатраты в рабочих днях (см. `build_rows` в `board_logic.py`).
5. Ось X — только рабочие дни горизонта планирования; суббота и воскресенье не отображаются (нулевая длина на шкале).
6. Даты в подсказке берутся либо из положения задачи на шкале, либо из полей Jira — в зависимости от `fields.*.source`.
7. Drag-and-drop между сотрудниками сразу меняет исполнителя на экране и добавляет запись в `pending_changes.json`; drag-and-drop внутри строки одного сотрудника меняет только порядок в браузере. Перетаскивание правого края прямоугольника меняет плановые трудозатраты и тоже копится в `pending_changes.json`. В Jira ничего не уходит до нажатия «Сохранить в Jira».
8. Выпадающий список в шапке страницы фильтрует диаграмму по значению поля `fields.sprint`; список спринтов строится из задач, загруженных в текущей выборке.

## Безопасность

- Не коммитьте `.env` с паролями.
- Учётной записи из `.env` нужны права **чтения** задач по вашему JQL и права **смены исполнителя** (assignee) и **редактирования трудозатрат** — приложение умеет писать в Jira только эти два поля, по кнопке «Сохранить». Если запись не нужна, используйте учётку без права редактирования — кнопка сохранения будет возвращать ошибку Jira, но чтение продолжит работать.
- Приложение предназначено для внутренней сети / локального запуска; отдельной аутентификации веб-UI нет — доступ к странице означает доступ к чтению задач и к отправке изменений в Jira от имени сервисной учётки из `.env`.
- Файл `pending_changes.json` (в корне проекта, добавлен в `.gitignore`) хранит несохранённые изменения в открытом виде; не коммитьте его и ограничьте доступ к серверу, где он лежит.
