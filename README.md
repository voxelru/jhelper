# jhelper

Flask-приложение для планирования задач из Jira: выборка по JQL, диаграмма «сотрудник × дата» с прямоугольниками трудозатрат.

Приложение **читает** задачи из Jira по JQL и умеет **точечно записывать** два изменения — исполнителя задачи и плановые трудозатраты (ширину прямоугольника), — когда пользователь явно нажимает «Сохранить в Jira». Никаких других полей приложение в Jira не меняет.

## Возможности

- Подключение к Jira (Server / Data Center) по **логину и паролю** (HTTP Basic Auth)
- Выбор задач по **JQL** из файла настроек
- Диаграмма:
  - **сверху** — даты (выходные на шкале не занимают место)
  - **слева** — сотрудники
  - **прямоугольники** — задачи в 3 строки: ключ со статусом, название, заказчик
  - ширина прямоугольника = плановые трудозатраты в рабочих днях
  - приглушенный цвет по **приоритету**
  - значок `!` рядом с ключом, если в Jira не заполнены дата начала, дата окончания или трудозатраты
  - **полностью заполненные** задачи (в Jira указаны и дата начала, и дата окончания, и трудозатраты) занимают на диаграмме строго свой диапазон дат — ширина блока равна реальному числу рабочих дней между этими датами, а не трудозатратам
  - остальные задачи (не хватает хотя бы одной из трёх величин) идут в очередь **после самой поздней** из полностью заполненных задач, подряд без зазоров, в порядке приоритета — без попытки автоматически заполнить более ранние промежутки, чтобы туда можно было вручную перетащить любую задачу
- Выпадающий **фильтр по спринту** в шапке страницы (значение берётся из поля Jira, настроенного в `fields.sprint`)
- Выпадающий **фильтр по бизнес-партнёру** в шапке страницы (значение берётся из поля Jira, настроенного в `fields.customer`)
- **Фильтр по датам** в шапке страницы: два поля «с» и «по» задают, за какие календарные дни строится шкала времени. Даты ничем не ограничены — окно можно увести в прошлое или в будущее, шкала перестраивается под него (кнопка ↺ возвращает вид по умолчанию: горизонт планирования от сегодняшнего дня). Задача, выходящая за границу диапазона, рисуется только своей попадающей в него частью — обрезанный край помечается пунктиром, а задачи целиком вне диапазона не показываются
- **Поиск** по номеру задачи и заголовку в шапке страницы — скрывает не подходящие задачи по мере ввода
- Все фильтры (спринт, бизнес-партнёр, даты, поиск) действуют одновременно
- Клик по прямоугольнику задачи (и ссылки с ключей задач) открывает её в Jira в новой вкладке, если задан `JIRA_BASE_URL`
- Кнопки **↩ отменить последнее действие** и **✕ отменить все изменения** в шапке страницы откатывают несохранённые изменения (исполнитель, даты и продолжительность) без обращения к Jira
- Всплывающая подсказка по задаче показывает ключ, название, заказчика, даты начала/завершения и трудозатраты
- **Любое перемещение или изменение размера задачи** записывает в `pending_changes.json` сразу **три параметра**: дату начала (`startDate`), дату окончания (`endDate`) и продолжительность (`effortDays`, плановые трудозатраты в рабочих днях). Частичных записей (только даты или только трудозатраты) не бывает — положение задачи всегда описано целиком
- **Перетаскивание задачи влево/вправо** ставит её на новую дату (день, на который отпустили прямоугольник) — задача становится «закреплённой» по сроку, как если бы обе даты были назначены в Jira
- **Перетаскивание задачи между сотрудниками** одновременно меняет исполнителя и положение (три параметра)
- **Изменение ширины прямоугольника** (перетаскивание правого края) задаёт новую продолжительность: левый край остаётся на месте, вместе с трудозатратами пересчитывается дата окончания
- Дата, у поля которой не задан `jira_field_id`, всё равно попадает в файл изменений (чтобы запись была полной), но при сохранении в Jira пропускается — писать её некуда
- Все несохранённые изменения (исполнитель и положение) сразу видны в UI (задача помечается как несохранённая) и копятся в локальный файл `pending_changes.json`
  - в Jira ничего не отправляется, пока не нажата кнопка **«Сохранить в Jira»** — она сохраняет все накопленные изменения одним действием;
  - до сохранения изменения переживают перезагрузку страницы (хранятся в файле на сервере), но не переживают повторный запрос `/api/board` от другого клиента, если тот сохранит поверх — данные читаются из этого же файла, поэтому конфликтов «последний выигрывает» стоит избегать при многопользовательской работе
- Горизонт планирования настраивается (по умолчанию 90 календарных дней)
- Задачи без исполнителя **не показываются**

## Требования

- Python 3.10+
- Доступ к Jira REST API (`/rest/api/2/search`/`/issue` или `/rest/api/3/search`/`/issue`)
- Учётная запись с правом **чтения** задач по вашему JQL **и правом смены исполнителя** (assignee) на задачах, которые может редактировать пользователь — это нужно для кнопки «Сохранить в Jira». Если такого права нет, кнопкой пользоваться нельзя, но чтение и просмотр доски продолжат работать.

## Настройка

### 1. Учётные данные Jira

Скопируйте `.env.example` в `.env` и заполните:

```env
JIRA_BASE_URL=https://jira.example.com
JIRA_USERNAME=login
JIRA_PASSWORD=secret
```

| Переменная       | Описание                          |
|------------------|-----------------------------------|
| `JIRA_BASE_URL`  | Базовый URL Jira без `/` в конце  |
| `JIRA_USERNAME`  | Логин                             |
| `JIRA_PASSWORD`  | Пароль                            |

Файл `.env` в git не коммитится.

### 2. Бизнес-настройки — `config/app_settings.yaml`

#### JQL

```yaml
jql: 'assignee is not EMPTY AND statusCategory != Done ORDER BY priority DESC'
```

Рекомендуется оставлять условие `assignee is not EMPTY`: задачи без исполнителя всё равно отфильтровываются на стороне приложения.

#### Приоритеты и цвета

Имена должны совпадать с `priority.name` в вашей Jira:

```yaml
priorities:
  order:
    - Highest
    - High
    - Medium
    - Low
    - Lowest
  colors:
    Highest: "#b85c5c"
    High: "#c68452"
    Medium: "#c2a24f"
    Low: "#6f9a76"
    Lowest: "#73879a"
    default: "#7f8f9b"
```

- `order` — порядок в очереди сотрудника (первый = самый высокий приоритет)
- `colors` — заливка прямоугольников; неизвестный приоритет берёт `default`

#### Горизонт планирования

```yaml
planning_horizon:
  kind: calendar_days   # или working_days
  count: 90
```

| `kind`           | Смысл |
|------------------|--------|
| `calendar_days`  | `count` календарных дней от сегодня; на шкале только рабочие дни внутри интервала |
| `working_days`   | `count` рабочих дней подряд; выходные не занимают место на шкале |

#### Трудозатраты (ширина блока)

```yaml
effort:
  type: timetracking_original
  jira_field_id: null

min_effort_working_days: 1
working_hours_per_day: 8
```

| `effort.type`             | Источник |
|---------------------------|----------|
| `timetracking_original`   | `timetracking.originalEstimateSeconds` → дни через `working_hours_per_day` |
| `timetracking_remaining`  | `timetracking.remainingEstimateSeconds` |
| `number_field`            | Число из поля (`jira_field_id`, напр. `customfield_10016`) как рабочие дни |
| `seconds_field`           | Число из поля как секунды → дни через `working_hours_per_day` |

Если оценка отсутствует или нулевая, используется `min_effort_working_days` (по умолчанию **1 md**).

#### Масштаб шкалы

```yaml
pixels_per_working_day: 36
```

#### Дополнительные поля Jira

```yaml
fields:
  customer:
    jira_field_id: null  # например customfield_10100

  sprint:
    jira_field_id: null  # например customfield_10007

  start_date:
    jira_field_id: null  # например duedate / customfield_...

  end_date:
    jira_field_id: null
```

- `fields.customer.jira_field_id` — кастомное поле Jira для заказчика; значение выводится 3-й строкой в блоке задачи и в подсказке.
- `fields.sprint.jira_field_id` — поле Jira со спринтом (обычно `customfield_XXXXX` от Jira Software); значение используется для выпадающего фильтра по спринту в шапке страницы. Поддерживаются оба формата поля Sprint — и современный (список объектов), и устаревший строковый формат Jira Server/DC.
- `fields.start_date.jira_field_id` и `fields.end_date.jira_field_id` — поля Jira для дат начала/окончания. Одна настройка управляет и чтением, и записью:
  - **задан** (например `duedate` или `customfield_...`) — если в Jira дата заполнена, задача встаёт на диаграмме фиксированно на эту дату (по дате начала, а если она не задана — вычисляется от даты окончания и трудозатрат); перетаскивание задачи или изменение ширины прямоугольника пишет новую дату обратно в это же поле Jira при нажатии «Сохранить в Jira»;
  - **`null`** — дата на диаграмме чисто расчётная (из положения задачи в очереди сотрудника, старая логика без привязки к датам) и никогда не записывается в Jira, даже если задачу перетащить.

## API

| Метод | Путь            | Описание |
|-------|-----------------|----------|
| `GET`  | `/`             | Страница диаграммы |
| `GET`  | `/api/settings` | Настройки для UI (горизонт, цвета, рабочие даты, источники полей, минимальные трудозатраты, URL Jira). Параметры `?from=&to=` (ISO `YYYY-MM-DD`, любые даты) задают окно шкалы вместо горизонта по умолчанию |
| `GET`  | `/api/board`    | Данные доски: строки сотрудников, задачи, списки спринтов/бизнес-партнёров для фильтров и метаданные для подсказок. Принимает те же `?from=&to=`; смещения задач считаются от начала окна и могут быть отрицательными (задача началась раньше окна) |
| `GET`  | `/api/pending`  | Список несохранённых изменений (из `pending_changes.json`) |
| `POST` | `/api/pending`  | Добавить/обновить несохранённую смену исполнителя. Тело: `{"key", "assigneeId", "assigneeName", "originalAssigneeId"}`. Если `assigneeId` совпадает с `originalAssigneeId`, запись удаляется (откат к исходному) |
| `POST` | `/api/pending/placement` | Записать положение задачи после любого перемещения или изменения размера — всегда тремя параметрами сразу. Тело: `{"key", "startDate", "endDate", "effortDays", "originalStartDate", "originalEndDate", "originalEffortDays"}`. Если все три значения совпали с исходными из Jira, все три удаляются из записи (откат к исходному); смена исполнителя в той же записи при этом сохраняется |
| `POST` | `/api/pending/undo` | Отменить последнее несохранённое действие (кнопка ↩), вернувшись к предыдущему состоянию `pending_changes.json`. История хранится в `pending_changes_history.json` (до 20 шагов) и сбрасывается после `/api/save` |
| `POST` | `/api/pending/clear` | Отменить сразу все несохранённые изменения (кнопка ✕). Само это действие тоже попадает в историю и может быть отменено через `/api/pending/undo` |
| `POST` | `/api/save`     | Отправить все несохранённые изменения в Jira (`PUT /rest/api/{2,3}/issue/{key}`): исполнителя, трудозатраты и даты. Даты без настроенного `jira_field_id` пропускаются (это не ошибка). Успешные части удаляются из pending-файла, неудачные остаются и возвращаются в `failed` (с полем `field`: `assignee`, `effort`, `startDate` или `endDate`); положение возвращается в файл целиком — все три параметра вместе |

Приложение пишет в Jira только по явному действию пользователя (кнопка «Сохранить в Jira») и только настроенные поля: исполнителя (`assignee`), плановые трудозатраты (`timetracking` или настроенное кастомное поле — см. `effort.type`) и, если задан `jira_field_id`, даты начала/окончания (`fields.start_date`/`fields.end_date`). Остальные поля (названия, приоритеты, статусы и т.п.) приложение в Jira не меняет.

## Как устроена диаграмма

1. Задачи загружаются по JQL и группируются по исполнителю.
2. При загрузке запрашиваются стандартные поля Jira (`summary`, `assignee`, `priority`, `status`, `timetracking`) и дополнительные поля из `effort`/`fields` (см. `collect_jira_fields` в `board_logic.py`), включая спринт.
3. Внутри строки задачи сортируются по `priorities.order`.
4. Задача считается **полностью заполненной** (`isComplete`), если в Jira заданы дата начала, дата окончания и трудозатраты (или всё это уже выставлено перетаскиванием/растягиванием на самой диаграмме и ещё не сохранено). Такие задачи занимают на диаграмме строго свой диапазон дат — ширина блока равна реальному числу рабочих дней между этими датами, трудозатраты на неё не влияют. Остальные задачи идут в очередь **после самой поздней** из полностью заполненных, подряд без зазоров: ширина блока ∝ трудозатраты в рабочих днях (см. `build_rows` в `board_logic.py`). Автоматического заполнения промежутков между полностью заполненными задачами нет — они остаются пустыми, чтобы туда можно было вручную перетащить любую задачу.
5. Ось X — только рабочие дни окна шкалы; суббота и воскресенье не отображаются (нулевая длина на шкале). По умолчанию окно — это горизонт планирования от сегодняшнего дня, а фильтр по датам заменяет его на любой выбранный интервал (в том числе целиком в прошлом): доска перезапрашивается с `?from=&to=`, и положение блоков считается от первого дня окна. Сами задачи и их даты при этом не меняются — это только окно просмотра.
6. Даты в подсказке берутся либо из положения задачи на шкале, либо из полей Jira — в зависимости от того, задан ли `fields.*.jira_field_id`.
7. Перемещение и изменение размера устроены одинаково: и то и другое приводит задачу к точному диапазону дат и записывает в `pending_changes.json` все три параметра сразу — `startDate`, `endDate` и `effortDays`.
   - Перетаскивание **влево/вправо** ставит задачу на дату точки отпускания (округляется до ближайшего рабочего дня), ширина сохраняется; задача сразу становится «полностью заполненной».
   - Перетаскивание **между сотрудниками** дополнительно меняет исполнителя (отдельная запись `assigneeId` в той же строке файла).
   - Растягивание правого края задаёт новую продолжительность, левый край (дата начала) остаётся на месте, дата окончания пересчитывается.
   - Если раскладка строки сдвинула задачу вправо от точки отпускания (впереди стоит другая задача с точными датами), в файл пишется фактическое положение блока, а не точка отпускания.
   - Возврат задачи ровно в исходное состояние (все три параметра совпали с Jira) удаляет запись о положении.
   - Всё это копится локально, в Jira ничего не уходит до нажатия «Сохранить в Jira».
8. Выпадающие списки в шапке страницы фильтруют диаграмму по значению `fields.sprint` и `fields.customer`; списки строятся из задач, загруженных в текущей выборке. Поле поиска дополнительно фильтрует по вхождению текста в ключ (`PROJ-123`) или заголовок задачи, без учёта регистра. Фильтры действуют одновременно (задача должна пройти все включённые).
9. Фильтр по датам («Даты: с — по») задаёт окно шкалы. Ограничений на выбор нет: доступна любая дата, в том числе раньше сегодняшнего дня; границы автоматически подтягиваются друг к другу, если «с» окажется позже «по». Если заполнена только одна граница, вторая достраивается по горизонту планирования, а слишком широкое окно подрезается до 400 рабочих дней (`MAX_WINDOW_WORKING_DAYS` в `board_logic.py`) — фактические границы возвращаются в ответе и подставляются в поля.
   - Задачи без дат (их не на что закрепить) раскладываются в очередь не раньше сегодняшнего дня, даже если окно начинается в прошлом: в прошлое их раскладывать бессмысленно.
   - Задача, начавшаяся раньше начала окна, получает отрицательное смещение и показывается обрезанной слева — видно только её оставшуюся часть.
   - Задача, начавшаяся раньше левой границы или заканчивающаяся правее правой, показывается частично: видна только та часть, что попадает в диапазон, обрезанный край рисуется пунктиром без скругления.
   - У задачи с обрезанным правым краем убирается ручка изменения размера — настоящая дата окончания вне окна, тянуть её вслепую нельзя.
   - Перетаскивание работает в координатах видимого окна: задача встаёт на тот календарный день, над которым отпустили блок.
   - Если в выбранном диапазоне нет ни одного рабочего дня, вместо доски выводится сообщение об этом.

## Безопасность

- Не коммитьте `.env` с паролями.
- Учётной записи из `.env` нужны права **чтения** задач по вашему JQL и права **редактирования** исполнителя (assignee), трудозатрат и, если у `fields.start_date`/`fields.end_date` задан `jira_field_id`, дат начала/окончания — приложение умеет писать в Jira только эти поля, по кнопке «Сохранить». Если запись не нужна, используйте учётку без права редактирования — кнопка сохранения будет возвращать ошибку Jira, но чтение продолжит работать.
- Приложение предназначено для внутренней сети / локального запуска; отдельной аутентификации веб-UI нет — доступ к странице означает доступ к чтению задач и к отправке изменений в Jira от имени сервисной учётки из `.env`.
- Файлы `pending_changes.json` и `pending_changes_history.json` (в корне проекта, добавлены в `.gitignore`) хранят несохранённые изменения и историю для отмены в открытом виде; не коммитьте их и ограничьте доступ к серверу, где они лежат.

Проект для внутреннего использования. При необходимости добавьте лицензию отдельно.
